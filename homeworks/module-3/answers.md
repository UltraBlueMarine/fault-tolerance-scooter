### 2. Подумайте, как помочь пользователю

**Какой механизм из урока подходит для временного сбоя?**

retry + backoff + jitter

**Как сделать так, чтобы отдельная ошибка Scooter не становилась ошибкой пользователя?**

Retry последовательно повторяет запрос с интервалом, поэтому вероятность ошибки для пользователя снижается с каждой попыткой. Например: 5% -> 0.25% -> 0.0125% -> 0.000625%.

**Как ограничить время ожидания, чтобы решение не нарушало цель 300 мс?**

Timeout + retryPolicy: `timeout: 250ms` ограничивает весь вызов вместе с повторами, худший случай `1.2 * (20 + 40 + 80) + 4 * RPC_p99 = 168 + 4 * RPC_p99 <= 250`.

## Задание 2 - Спасение утопающего

### Конфигурация

```yaml
retry:
  __default__:
    enabled: false
    separate_retry_per_handler_enabled: false

    # p = 0.05 (Unavailable rate), N = 6000 requests, n = max_attempts, m = backoff_multiplier
    timeout: 250ms # p99_target - margin = 300 - 50; worst: 1.2*sum_backoff + n*RPC_p99 <= timeout -> 168 + 4*RPC_p99 <= 250
    max_attempts: 4
    # p^n - user error;
    # N*p^n - expected errors;
    # P(0 errors) = (1 - p^n)^N ~ e^(-N*p^n); n=3 -> 47%, n=4 -> 96%
    initial_backoff: 20ms
    # initial_backoff_max = (timeout - n*RPC_p99) / 1.2 / S,
    # S = 1 + m + ... + m^(n-2) = 7
    max_backoff: 80ms # = initial_backoff * m^(n-2), last pause; with jitter (x0.8..1.2) up to 96ms
    backoff_multiplier: 2 # = (max_backoff / initial_backoff)^(1/(n-2)) = (80/20)^(1/2); sum_backoff = initial_backoff*(m^(n-1) - 1)/(m - 1) = 140ms
    retryable_codes: [Unavailable]
    throttler:
      throttling_enabled: true
      throttle_max_tokens: 26
        # N = 600
        # допустимый процент = 2%
        # B = floor(600 * 2 / 100) = 12
        # M = 2 * (B + 1) = 2 * 13 = 26
        # порог = M / 2 = 13
        # итого попыток <= N + B = 612
      throttle_token_ratio: 0.1

  handlers:
    - method: /scooter.scooter.v1.ScooterService/GetScooter
      enabled: true
```

### 1. Посмотрите, что делают ретраи при полном отказе

**Генератор получит 600 ошибок - 100%. Но сколько обращений ушло в зависимость?**

2400, из них 1800 - ретраи.

**Как ограничить дополнительную работу всего потока, а не только одного запроса?**

Общий бюджет для всех запросов через одно соединение.

### 2. Выберите и реализуйте политику бюджета

**Определите, какую долю дополнительных попыток относительно 600 исходных запросов вы готовы допустить при полном отказе. Выберите предел меньше 100%, допускающий хотя бы один повтор на 600 запросов, - например, 1-5% - и объясните, почему такая дополнительная нагрузка приемлема.**

 N = 600

 допустимый процент = 2%

 B = floor(600 * 2 / 100) = 12

 M = 2 * (B + 1) = 2 * 13 = 26

 порог = M / 2 = 13

 итого попыток <= N + B = 612

Когда сервер упал полностью, повторы только усугубят проблему: будет сделано 2400 запросов, а если пользователей не один, а 10 тысяч, они просто положат Scooter.

В начале сбоя может быть непонятно, это полный отказ или временная неполадка. Поэтому лучше сделать бюджет, который позволит сделать пару ретраев. Когда бюджет будет исчерпан, Gateway перестанет делать ретраи, пока успешные запросы его не восполнят. Плюс по заданию было непонятно, какой запас мощности у сервера (верхняя граница), поэтому ratio выбирал только по нижней границе.

12 лишних запросов на 600 (+2%) против +300% без бюджета. Такая добавка упавший Scooter не добьёт.

**Отдельно выберите `throttle_token_ratio`: сколько успешных RPC должно компенсировать одну ошибку?**

 нижняя граница: p / (1 - p) = 0.05 / 0.95 ~ 0.053

 20 * 0.0526 ~ 1.05 токена списывается в секунду при 5% ошибок

 верхняя граница - это запас мощности, который сервер может выдержать, допустим 10-20%

 p / (1 - p)   <=   throttle_token_ratio   <=   запас мощности зависимости

 throttle_token_ratio = 0.1 значит, что 10 успешных RPC компенсируют 1 ошибку. Пополнение 20 * 0.1 = 2 токена/с больше списания 1.05, поэтому при 5% шума бюджет остаётся полным.
